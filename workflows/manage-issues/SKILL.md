# Manage Issues

Turn a bounded issue backlog into a traceable queue; reports are read-only and triage does not implement issues.

## Workflow

1. Confirm repository, scope, applicable user, project, and nested rules, loaded principles, current inventory, and permitted effects. Before producing a substantive triage candidate, define its validation contract: candidate, mode, Definition of Done, criteria, evidence, and useful perspectives.
2. Classify evidence-backed keep, refine, split, duplicate, realign, stale, close, and blocked decisions. Record canonical links, owner, blocker, intended effect, and the smallest next action.
3. Recommend the first coherent slice with its expected outcome and dependencies. Ask only for a consequential choice or missing authority; decide reversible triage details from evidence.
4. For a substantive triage candidate, use [Quality Validation](../../capabilities/capability-quality-validation/SKILL.md) before hosted writes. If unavailable, self-assess; obtain distinct review and critique with subagents, or assess them sequentially only when independence is not required; otherwise return BLOCKED. Triage findings, improve the candidate, and request fresh affected verdicts until PASS. Use direct checks for mechanical work.
5. Apply only the authorized, validated subset, preserving context and recoverable closure, then read back changed fields. Recheck only after changed evidence or a repair; on unchanged evidence, change approach or return the cause, options, recommendation, consequence, and next action.

## Definition of Done

- Repository, scope, inventory, and criteria are identified.
- Decisions have evidence, ownership where relevant, and a recommended first slice.
- Read-only work returns a traceable proposal without hosted mutation.
- Authorized writes are selected and read back.
- Completion requires current mode-specific acceptance: every required criterion has proof, applicable review and critique scopes accept, and no required finding remains.
